@eco

上下文窗口是 Agent 唯一的「视野」——模型没有记忆，每次推理只能看到当下拼装出的这份上下文，没进窗口就等于不存在。**上下文工程**的核心命题：在有限 token 预算内决定塞什么、怎么排、何时压缩、什么卸载。拆成三机理——装配定质量下限、前缀缓存省钱省时、压缩卸载扩容量，缓存与卸载是两条旁路，三者协同榨干每个 token 价值。见生态图。

@c1

**上下文装配**把散落原料拼成「刚刚好」的上下文，分层：系统提示→工具定义→检索知识→对话历史→用户输入。顺序有讲究——前置内容稳定利于缓存，模型对首尾更敏感、中段易忽略（**lost-in-the-middle**）。三原则：分层拼装、相关性排序（关键证据放易注意位）、按预算裁剪降级而非硬塞。它是整链质量下限，再强的缓存压缩都救不回糟糕装配。见图。

@c2

**前缀缓存**是最直接的成本杠杆：推理时为每个 token 计算并缓存 KV-Cache，若两次请求前缀逐字节相同即可复用，省算力/延迟（TTFT）/费用。关键在让前缀「稳定」——系统提示、工具定义放最前，上下文 **append-only**，时间戳/随机 ID 后置或剔除。**一个字节变动，缓存从变动点全线失效**。命中率是核心指标——衡量你多会省钱。见图。

@c3

**压缩与卸载**让 Agent 在有限窗口跑长任务。**压缩**让 LLM 把冗长历史摘要成要点（保留决策/结论/约束、丢过程噪声），代价有损、压过头丢细节；**卸载**把细节写外部存储（向量库/文件/DB），窗口只留可回溯指针，代价增 IO 延迟。实践常「分级」：热数据留窗口、冷数据卸载，压缩前留原文备份可回滚。底线：**有损压缩必须可控、关键信息零丢失**。见图。

@cmp

三机理分工：装配解「素材噪声与顺序不当」（靠分层/排序/裁剪，代价需精心设计）、前缀缓存解「长前缀重复计算」（靠稳定/append-only/复用 KV，代价一变即失效+受 TTL 容量限）、压缩卸载解「长任务撑爆窗口」（靠摘要+外部卸载，代价压缩有损/卸载增 IO）。协同而非三选一：装配定质量、缓存定成本、压缩卸载定任务时长。四维对照见图。

@eng

三条底线：**预算即纪律**——token 是硬约束，先定预算再装配，靠相关性排序与首尾摆放对抗 lost-in-the-middle，每层可裁剪降级；**缓存即成本杠杆**——系统提示/工具定义前置、前缀 append-only、动态内容后置，命中率是核心指标；**压缩不失真**——摘要保留决策/结论/约束，细节卸载留可回溯指针，分级存放热冷、压缩前留备份。核心：上下文窗口既是能力边界也是成本账单。详见图。

**2025 前沿**：随着 Agent 多轮调工具、上下文越滚越长，两个新病症浮出水面——**上下文疲劳**（context fatigue，窗口被无关历史与冗余观察塞满后，模型注意力被稀释、指令遵循与推理质量随长度衰减，不是塞得下就等于用得好）与**工具输出爆炸**（tool-output bloat，一次检索/一个 API 返回动辄上万 token 的原始 JSON，几轮就撑爆窗口）。应对手段随之标准化：工具结果先摘要/字段裁剪再入上下文而非原样回灌、过期观察主动逐出、长任务周期性「压缩重启」（把历史压成状态快照重新开局）。这标志着「上下文工程」已取代「提示工程」成为 Agent 落地的核心工艺——决定成败的不再是提示词措辞，而是全程如何治理这份动态膨胀的上下文。
